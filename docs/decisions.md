2026-10-03: Pin n8n to `n8nio/n8n:2.41.6` — latest stable at P0; satisfies the ≥ 2.20.0 requirement for instance-level MCP (`N8N_MCP_ACCESS_ENABLED`).
2026-10-03: Pin Postgres to `postgres:17.11-alpine3.23` — 18.x changes the data directory layout/volume path; 17 is stable and supported by n8n, nothing here needs 18.
2026-10-03: One login role per database (`n8n` owns db `n8n`, `ops_app` owns db `ops`), created by `db/init/` on first start — n8n's Postgres credential for app data can't touch n8n internals, and vice versa.
2026-10-03: Migrations run by a one-shot `migrate` compose service (plain `psql` + `schema_migrations` table with sha256 checksums); n8n waits for it to exit 0 — no extra tool (Flyway/sqitch) for a handful of SQL files; edited-after-apply migrations abort loudly.
2026-10-03: Migration 001 contains only `audit_log` (append-only via triggers); domain tables land in the phase that first uses them (suppliers/POs/receiving in P1, invoices in P2, reconciliations in P3) — avoids locking in an invoice schema before the idempotency vs. duplicate-detection semantics are settled.
2026-10-03: Exported workflow files are named by slugified workflow name, and export strips `pinData`, `staticData` and volatile metadata (timestamps, version ids, sharing) — readable filenames, no execution payloads in git, and a re-export of unchanged workflows is byte-identical (enforced in CI).
2026-10-03: Workflow ids are preserved in exports — import updates in place, so `import.sh` is idempotent.
2026-10-03: gitleaks runs from the pinned `zricethezav/gitleaks:v8.30.1` image rather than gitleaks-action — same binary locally and in CI, no licence key.
2026-10-03: Host ports bind to 127.0.0.1; Postgres defaults to host port 5433 and Ollama to 11435 — dev machine already runs Postgres on 5432 and may run a native Ollama on 11434.
2026-10-03: `description_mismatch` is a labelled *condition*, not a flag reason — a line worded differently from the PO is what fuzzy matching is for; if item, quantity and price match, the right outcome is `recommend_approve`. Ground truth records the true PO-line mapping so P3 can score the matcher directly.
2026-10-03: `unknown_po` and `missing_po` are flag reason codes (expected `flag`), not `needs_review` — they are clear rule failures with a reason a human can act on; `needs_review` stays for extraction/matching we can't trust.
2026-10-03: Price tolerance 2% (unit price above PO); GST tolerance `ceil(taxable_lines / 2)` cents against 10% of the taxable subtotal, using the PO's GST status — per-line rounding is legitimate, and the invoice's own GST markers can be wrong. P3 must use the same values or explain why not.
2026-10-03: Invoice key is `sha256(abn_digits | UPPER(TRIM(invoice_number)) | total_cents)` with `|` separators — plain concatenation lets ("INV1", 23) collide with ("INV12", 3).
2026-10-03: Duplicates are generated as different files with the same key (half visibly stamped, half differing only in PDF metadata); byte-identical re-sends are a separate case with expected ingestion `noop`. Proposal for P2, not yet decided: skip on identical file hash, flag `duplicate_invoice` on same key with a different file.
2026-10-03: Generated data is not committed; output is deterministic (reportlab invariant mode) and the gate report is committed at `docs/synthetic-data-report.md`, with a test that fails if it goes stale.
2026-10-03: `seed.sql` records a fingerprint of the master data and refuses to load over data from a different seed or generator version — with ON CONFLICT DO NOTHING, same-numbered POs would otherwise silently keep stale lines.
2026-10-03: GST treatment follows broad Australian rules (fresh food GST-free; alcohol, chemicals, amenities, services, snacks taxable), simplified for a demo — it gives mixed GST invoices, which is what makes the GST check worth having.
2026-10-06: P2 ingestion trigger is an upload webhook — the eval harness calls the same endpoint as the demo, so the measured path and the shown path are identical. A watched folder or IMAP mailbox can sit in front of it later.
2026-10-06: P2 evaluates Ollama only (local, RTX 4060); the Anthropic comparison is out of P2 scope — no API key or spend for now. Revisit at the P2 gate if the local model misses the targets. CLAUDE.md's open decision on provider stays open until then.
2026-10-06: P2 accuracy targets confirmed — total, invoice number and PO number >= 98% exact match; line items >= 90% (a line counts only if description, quantity, unit price and line total all match).
2026-10-06: Duplicate handling supersedes CLAUDE.md principle 4's single key — idempotency is by file sha256 (identical bytes are a no-op); the same sha256(abn|invoice_number|total_cents) key with a different file is stored with `duplicate_of` set and flagged `duplicate_invoice` in P3. Keying on invoice_key alone would silently drop duplicates and make that flag unreachable.
2026-10-06: Ingestion is two tables — `invoice_files` (one row per file hash, including needs_review failures and the raw model output) and `invoices`/`invoice_lines` (validated extractions only) — failures have no valid data for typed columns, and a file that failed review must not be silently retried on re-upload.
2026-10-06: invoice_key is computed by Postgres (`invoice_key_of()`, a generated column), not in the workflow — one definition, checked against data-gen's Python version in tests and CI. IMMUTABLE is asserted by hand since convert_to() is only STABLE; the ops database is UTF8.
2026-10-06: The LLM transcribes, code calculates — the extraction schema returns money as dollar strings exactly as printed (`"1430.74"`), not cents or floats; conversion to cents, ABN normalisation and calendar-date validation are done in code. The model is told not to recalculate or correct totals, so a miscalculated GST on the invoice is extracted faithfully and caught by deterministic reconciliation.
2026-10-06: Extraction schema omits supplier address, email and phone (reconciliation never uses them; they'd only add noise to the accuracy numbers). Ground truth still carries them.
2026-10-06: Ground truth `document.lines[].unit` is null where the template prints no unit (till-receipt template C prints one only for kg) — an extractor can't be scored against a value that isn't on the page. `labels.lines` is unaffected. Similarly the generator never lets a taxable line print GST 0.00 on per-line-GST invoices.
2026-10-06: The extraction evals use the native Windows Ollama (port 11434) rather than the compose `local-llm` profile — it already sees the RTX 4060 and the host was verified; GPU passthrough through Docker is untested and was not needed. The compose profile stays for machines without a native install.
2026-10-06: Candidate models for 8 GB VRAM are `qwen3.5:9b`, `gemma4:e4b` and `qwen3.5:4b` (a cheap lower bound), chosen from the Ollama library listing. Text models suffice because the input is the PDF text layer, not an image.
2026-10-06: Eval protocol — prompt wording and model choice are tuned on a separate dev set (seed 7, 60 invoices); the gate set (seed 42) is run once at the end with prompt and model fixed. Disclosure: five seed-42 invoices were used in a smoke run before the split, and it informed three prompt fixes (no invented `each` unit on layouts that print none; never compute per-line GST; copy a printed 0.00 instead of null). See evals/README.md.
2026-10-06: Eval context window is 4096 tokens — measured: `qwen3.5:9b` runs 100% on the GPU at 4096 but spills 12% to CPU at 6144 (and at 8192). The embedded schema drops its `description` fields (the rules are already in the prompt body) to leave retry headroom, and every run reports invoices within 5% of the limit because Ollama truncates silently.
2026-10-06: Eval scoring is strict and defined in evals/README.md — exact cents, exact invoice and PO numbers, a line is correct only if description, quantity, unit price and line total all match, lines are matched as a bag (a missed line does not shift the rest), exact re-sends are excluded. Reports carry 95% Wilson intervals because 98% on 196 invoices allows only 3 misses.
2026-10-06: The prompt lives in `prompts/invoice_extraction.md` as the single source of truth for the eval and, later, the workflow; `docs/prompts.md` mirrors it (CLAUDE.md requirement) and a test fails if they differ.
2026-10-06: The n8n Code node can use the real `ajv` validator — verified in the pinned image: `NODE_FUNCTION_ALLOW_EXTERNAL=ajv/dist/2020,ajv-formats` (the allowlist matches exact module names, so the subpath must be listed; `ajv` alone does not permit `ajv/dist/2020`). The workflow will validate against `schemas/invoice_extraction.json` directly rather than a hand-mirrored copy.
2026-10-06: OPEN — constrained decoding. The harness can constrain Ollama to the JSON schema, but n8n's Ollama chat model node only offers generic JSON mode. The eval gained `--format-mode schema|json|none` to measure what the node can reach. Decide at the workflow step: chat model node (provider swap by config) versus an HTTP Request node to Ollama (exact parity with the eval).
2026-10-06: `.gitleaks.toml` extends the default rules and allowlists exactly one value, the public SHA-256 test vector for `invoice_key()`, which gitleaks otherwise reports as an API key; verified that a different 64-hex string next to `api_key` is still caught.
2026-10-07: SUPERSEDES the 2026-10-06 entry on ajv in the Code node — ajv can be imported but cannot run there: the task-runner sandbox forbids code generation (`EvalError: Code generation from strings disallowed`) and ajv compiles validators with `new Function`. The `Validate Extraction` node instead interprets `schemas/invoice_extraction.json` itself (about 60 lines), supporting exactly the keywords our schemas use and THROWING on any other, so a schema change can never be silently ignored. No external modules are allowed in Code nodes (`NODE_FUNCTION_ALLOW_BUILTIN=crypto,fs` only). `tests/test_workflow_code.py` runs the workflow's real JS under Node against the Python validator on 2,232 generated valid and mutated outputs and requires identical verdicts; it found 28 genuine disagreements before the fix below.
2026-10-07: Python validation anchors every schema `pattern` with `\Z` — Python's `$` also matches before a trailing newline, so `"1430.74\n"` passed in the eval but fails in the workflow (ECMA-262) and in Postgres. The eval validator now behaves as the workflow does; both also reject years before 1900, quantities with more than 3 decimals, and money wider than 12 integer digits (the limits of `numeric(12,3)` and bigint cents).
2026-10-07: Ingestion logic lives in Postgres functions, not workflow expressions — `ingest_invoice(payload)` (dollars to cents, ABN digits, supplier lookup, duplicate detection, inserts, audit row in one transaction), `record_needs_review(payload)` and `invoice_file_status(sha)`. Principle 1 (deterministic logic is plain code or SQL) and testability: `db/tests/ingest.sql` asserts them with psql alone, in CI. Migration 004 also fixed 003: `invoice_lines.unit` may be null (the schema allows it) and `invoice_files.attempts` may be 0 (a PDF with no text layer never reaches the model).
2026-10-07: A model-server failure is not the model's fault — only unparseable model output counts as a validation failure and gets the one retry. A refused connection, timeout or 5xx fails the execution instead: audited by the Error Handler, HTTP 5xx to the caller, and the file is NOT recorded, so uploading it again after the outage works. Recording it as `needs_review` would have made an outage permanent for every file that arrived during it, because a recorded file is never silently reprocessed. The eval mirrors this: `TransportError` stops a run (resumable with `--resume`) instead of scoring as an extraction failure.
2026-10-07: n8n's chain node with Ollama JSON format parses the reply itself and emits the invoice fields directly instead of `{text}`; the validator accepts both shapes, and the chain node is set to continue on error so an unparseable reply becomes data for the retry rather than a failed execution.
2026-10-07: The retry is ONE user message (invoice text, the failed output, the numbered errors) built from `prompts/invoice_extraction_retry.md`, not extra chat turns — the chain node takes a single prompt and the workflow must send exactly what the eval measured. Matches CLAUDE.md ("validation error appended to the prompt"). Mirrored in docs/prompts.md and covered by the same drift test.
2026-10-07: BUG FIX with consequences — `strip_descriptions` removed every key named `description`, including the line item's `description` property, so the schema embedded in the prompt had no definition for that field. The model still got it right (it is in `required` and the prose), but the eval was not testing the prompt the workflow sends. Fixed (only string-valued annotation keys are dropped), a regression test added, and ALL dev-set results were discarded and regenerated with the corrected prompt.
2026-10-07: The ingestion webhook requires an `X-Ingest-Token` header (n8n header-auth credential), accepts only PDFs up to 10 MB (415 and 413 otherwise) and never records a rejected upload. Credentials are created from `.env` by `scripts/setup-credentials.sh` with fixed ids (so exported workflows reference id and name only), streamed over stdin into the container, never written to disk or the repo. Run it once after `docker compose up`, before `import.sh`.

The Error Handler is published too: an error workflow that is not published is never called. It records `workflow.error` to `audit_log`; the notification half of CLAUDE.md's Error Handler arrives in P4 with the approval channel decision.

2026-10-07: P2 model is `qwen3.5:9b` through n8n's Ollama Chat Model node (JSON format, temperature 0, `think: false`, context 4096). Dev set (seed 7, 59 scored invoices, corrected prompt), headers all 100% for the 9B and gemma: `qwen3.5:9b` 248/248 lines and 59/59 invoices fully clean at about 16s per invoice; `gemma4:e4b` 246/248 lines and 96.6% clean at about 5s (a viable fast alternative); `qwen3.5:4b` 232/248 lines (93.5%), total 98.3%, 81.4% clean at about 8s (too weak). 2026-10-07: RESOLVES the open question on constrained decoding — n8n's Ollama node offers only generic JSON mode, and that is enough for the chosen model: on the dev set the 9B's and gemma's raw replies were byte-identical in schema mode and JSON mode (59/59 each). It is NOT enough for weak models: the 4B sent 2 invoices to `needs_review` in JSON mode that schema mode handled. So the chat model node is kept (providers swap by configuration, as CLAUDE.md intends) and the 4B is ruled out on accuracy; an HTTP Request node to Ollama (schema-constrained) is the fallback if a smaller model is ever needed.
2026-10-07: `line_gst`, `unit` and `gst_applicable` are not trustworthy and nothing downstream may rely on them — observed through the workflow: the model sometimes invents a per-line GST amount on layouts that print none, returns null instead of `0.00` where they do, and says "each" where no unit is printed. They are outside the gate targets and not needed by reconciliation (GST is judged from line totals and the PO's GST status). Migration 005 records this as column comments; evals report them per field. The prompt was NOT tuned further on the gate set to improve them.
2026-10-07: GATE RUN 1 FAILED on line items — seed 42, 196 scored invoices, through the workflow with n8n's `Extract From File` and `qwen3.5:9b`: total, invoice number and PO number each 100% (196/196, 95% CI 98.1 to 100), but line items 86.8% (762/878) against the 90% target; every duplicate and re-send was handled correctly. Report kept as `evals/results/extraction-n8n-run1-seed42.md`. Of the 116 wrong lines, 95 were description-only errors (77 trailing words or numbers dropped, such as "Carton 200" becoming "Carton", 18 quantity and unit appended to the description) and quantity, unit price and line total were all correct on 859 of 878 (97.8%); the rest were amount errors (3 where the model added GST into a line total).
2026-10-07: ROOT CAUSE found by controlled comparison on identical dev invoices, not by tuning on the gate set — the same 59 dev invoices score 248/248 lines with Python's `pypdf` text but 226/248 (91.1%) with n8n's `Extract From File` text, with the same model and prompt. n8n space-joins every cell of a table row, so the model cannot tell where a description ends or which trailing number is the line total and which the GST; pypdf puts one cell per line. The hand-written eval had been feeding the model text the workflow never produces; the gate run, which goes through the workflow, is what exposed it.
2026-10-07: PDF text comes from a small `pdf-text` service (`services/pdf-text`, a compose service, internal network only) running the same `pypdf` code as the eval harness, replacing `Extract From File` — a deterministic fix for a deterministic problem, preferred over adding ever more prompt rules for a model to follow. `evals/run.py` imports the service's own function and a test enforces it (and that the pypdf pins match), so the eval and production cannot see different text again. Failure semantics unchanged: the service being down fails the execution (5xx, audited, file not recorded); a PDF it cannot read (corrupt, encrypted) returns empty text and the error, and ends in `needs_review` with the reason. With the service and an UNCHANGED prompt, the workflow scores 248/248 lines (100%) on the dev set, equal to the direct harness. CLAUDE.md's "Extract From File (PDF text)" is amended accordingly.
